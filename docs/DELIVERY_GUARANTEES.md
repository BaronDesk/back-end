# Delivery guarantees: agent ⇄ backend

What each message on the `/agent-ws` socket can promise: whether it arrives, whether it is kept while the link is down, and whether it is safe if it is received twice. Read this before changing a message handler, the command queue or the agent's outbox. A change that weakens one of these guarantees can break billing or lose an alert.

## The rule

> **Anything about money or security must never be lost and must be safe if received twice. Live stats are best effort.**

- **Money**: anything that starts, stops, extends or settles metering, or that moves a wallet. This covers session lifecycle, lock state, leases and settlement.
- **Security**: anything that locks or unlocks a PC, admits a gamer, or reports theft or tampering. This covers logins, LOCK/UNLOCK, credentials, and `anti_theft` / `security_violation` alerts.
- **Live stats**: telemetry and peripheral snapshots. The next frame replaces them, so losing one is acceptable.

"Never lost" can be met in two ways. The message itself is delivered, or the backend reaches the same effect from server state (for example, a LOCK that cannot be delivered is applied to the session and enforced on reconnect). Failing closed (the station locks, and no money moves) counts as safe. Silently doing nothing does not count.

## How to read the tables

- **Guaranteed to arrive?** Is the message itself, or its effect, sure to reach the other side once the link works?
- **Kept while offline?** If the link is down when the message is produced, is it stored and delivered or applied later?
- **Safe if received twice?** Does a duplicate (a retry, a resend or a replay) leave the same result as one copy?
- **How it's ensured**: the code that makes it true. Backend paths are relative to `src/`. Agent behaviour is from the agent repository and is not checked here.

Transport facts that apply to every agent → backend frame:

- **Per-connection replay guard** (`infra/realtime/seq-guard.ts`, `SeqGuard.check`). On each connection, a frame whose `seq` is not above the last one is dropped, and so is a frame whose `ts` is more than 30 s from server time. So the same frame delivered twice on one connection is processed once. A resend on a *new* connection gets a new `seq` and is processed again: that case is what the "safe if received twice" column covers. `telemetry` and `device_event` have their own guard (`TELEMETRY_STREAM_TYPES` in `modules/ops/agent.gateway.ts`).
- **No application-level ack** exists for any agent → backend frame except command replies. The backend never confirms that it received a `heartbeat`, `state_report`, `alert` and so on. If the backend drops or fails to process such a frame (it logs the error in `AgentGateway.handleMessage`), the agent does not know and does not resend.
- **Frames before the handshake** are ignored (`AgentGateway.handleMessage`, `conn.ready`).

## Backend → agent (frames that are not commands)

These frames have no ack and no retry. The backend writes them only to a live, handshaken socket (`AgentGateway.send` / `sendControl`).

| Message | Guaranteed to arrive? | Kept while offline? | Safe if received twice? | How it's ensured |
|---|---|---|---|---|
| `heartbeat_ack` | No, but it fails closed. The lease it carries is the only thing that keeps the PC unlocked: if an ack is lost, the lease lapses and the agent locks itself. | No | Yes. The lease is absolute (`serverTime` + `leaseSeconds`). | `AgentGateway.onHeartbeat` / `renewLease`, `SessionLoginService.lease`. The lease is 0 without a granted session, or when the session is paused for a staff or funds lock. If the renewal cannot be computed, the backend re-sends what is left of the current lease, without extending it. |
| `login_result` | No. If it is lost, the agent times out after 15 s. | No | Yes on the agent side: it is matched to the request by `requestId`. | `AgentGateway.onLoginRequest`. It is always sent before the session UNLOCK. |
| `station_credential` | No. It is sent again on each handshake while the token is near expiry. | No. A station offline until its token expires cannot reconnect, and must be enrolled again. | Yes. The agent stores the newest token. | `AgentGateway.onHandshake` → `StationAuthService.renewalFor` (`modules/station/services/station-auth.service.ts`). |

## Backend → agent: commands

Every command follows the same path (`modules/ops/services/commands.service.ts`, `modules/ops/services/command.processor.ts`):

1. A COMMAND row is created and a BullMQ job is added with `jobId = commandId`, so a double enqueue does nothing (`CommandsService.dispatch` / `enqueue`).
2. The worker marks the command SENT and sends it **only if the station is connected at that moment**. It then waits `COMMAND_ACK_TIMEOUT_MS` (default 10 s) and retries on timeout or on a failed socket write, up to `COMMAND_MAX_ATTEMPTS` (default 2), always with the same `commandId`.
3. A command the station did not receive (not connected, or no ack after the last attempt) goes to `CommandsService.resolveUndelivered`. A **staff** LOCK or END_SESSION for a session still open is applied from server state and ends `APPLIED_ON_RECONNECT` (`APPLIED_WHILE_OFFLINE`, `applyWhileOffline`). Any other command ends FAILED or TIMEOUT and **is never delivered later**.
4. Agent: it keeps the last 256 handled command ids and re-acks a duplicate without running it again. So resending the same `commandId` is safe. A *new* `commandId` with the same intent runs again.
5. When the station is offline at issue time, a staff command gets 409 `STATION_OFFLINE`, except a LOCK or END_SESSION that can be applied from server state. A system command (`SYSTEM_ACTOR_ID`) is skipped and logged (`CommandsService.issueSystem`).

| Command | Guaranteed to arrive? | Kept while offline? | Safe if received twice? | How it's ensured |
|---|---|---|---|---|
| `LOCK` (staff) | Yes, in effect. It is delivered, or applied from server state. | Yes. `APPLIED_ON_RECONNECT`: an ACTIVE session is paused at the last contact with `lockReason = staff`. The heartbeat lease becomes 0. On reconnect the session is not resumed, and a LOCK is sent again if the station reports itself unlocked. | Yes. Agent dedup by `commandId`, and locking a locked PC does nothing. | `CommandsService.issue` (`markStaffLock` before dispatch), `resolveUndelivered` → `StationLinkService.lockWhileOffline`, `StationLinkService.reconcile` (`resumesOnReconnect`, `issueSystemLock`), `SessionLoginService.lease`. |
| `LOCK` (system: runout, reconnect) | Only while the station is online and acks within 2 attempts. A timeout ends TIMEOUT and is not sent again. | Partly. The session keeps `lockReason = runout`, so after an offline pause the reconnect keeps it locked and re-sends LOCK. | Yes, as staff LOCK. | `SessionRunoutService.lockForRunout` (sets `lockReason` first), `CommandsService.issueSystemLock`. See Gaps for the online-timeout case. |
| `UNLOCK` (session: after login, resume, top-up) | No. A timeout or an offline station ends FAILED/TIMEOUT. It fails closed: the station stays locked, and no metering starts until the station reports itself unlocked. | No. On reconnect, `reconcile` issues a fresh UNLOCK for a session that is still granted. | Yes. The agent dedups by id, and a fresh UNLOCK for the same session binds the same session. | `AgentGateway.onLoginRequest` → `CommandsService.issueSessionUnlock`, `StationLinkService.reconcile`, `SessionRunoutService.onWalletCredited` (the funds lock is restored if the UNLOCK is not sent). Metering starts only from a reported `locked=false` (`handleStationStatus`). |

| `SHUTDOWN` | No. Refused with 409 while offline; FAILED/TIMEOUT if not acked. The session is **settled before** the command is sent, so billing does not depend on delivery. | No | Yes, within the agent's 256-id dedup window. | `CommandsService.issue` → `StationLinkService.closeForShutdown` → `SessionMeteringService.settle` (shared debit key). A settled session gets a 0 lease, so the PC locks even if SHUTDOWN is lost. |
| `LAUNCH_GAME` | No. Refused with 409 while offline, and when the station is locked or has no session. | No | Agent dedup by id. A new command id launches again. | `CommandsService.issue` (`agentStateOf`, `GamesService.findLaunchable`). `runningGameId` comes only from `state_report`. |
| `END_SESSION` (staff) | Yes, in effect. It is delivered, or applied from server state. | Yes. `APPLIED_ON_RECONNECT`: the session is closed as a force-close, billed up to the last contact. On reconnect, `reconcile` finds it closed and sends a system END_SESSION. | Yes. Settlement shares the debit key `session-settlement:<id>` and the session closes once (`SessionsRepository.complete`). The agent dedups by id. | `CommandsService.issue` / `resolveUndelivered` → `StationLinkService.endWhileOffline` → `closeFromServerState`, `StationLinkService.reconcile`. | `END_SESSION` (system: window over, force-close, stale session) | Not by itself. | `CATALOG_UPDATE` | No. It is sent only to online stations, with at most one open per station. | No, and not needed: the agent syncs its catalog on every connect. | Yes. The agent re-pulls the latest catalog. | `CommandsService.requestCatalogSync` (`repo.hasOpen`). |
| `POLICY_UPDATE` | Yes, in effect. It is re-sent on every (re)connect, so a lost one is replaced at the next connect. | Yes, in effect. Other frames on the socket, kept here for completeness: `session_notice` (backend → agent, display only, no ack: best effort) and `device_event` (legacy agent → backend; the current agent sends `alert`; duplicates are suppressed for 24 h in `AlertsService.onDeviceEvent` / `firstDelivery`).

## Gaps

These messages break the rule today: they concern money or security, and they can be lost or are not safe twice.

1. **`alert`: an anti-theft or security alert can be lost.**
   - The backend never acks an alert. The agent's outbox therefore treats a frame as delivered once the socket write succeeds. If the backend then fails to process it (a DB error, a station not resolved, a malformed payload), or the replay guard drops it, the alert is gone.
   - The outbox also drops its oldest entries when it is full, and drops a message after 10 failures while connected. During a long outage the oldest anti-theft alerts are the ones that are lost.
   - Not verified here: if the agent sends an outbox entry with its original `ts`, a backlog older than 30 s is rejected by `SeqGuard` (`ts_out_of_window`). That would lose every alert queued during an outage. Check that the agent stamps `ts` and `seq` at send time.
   - Fix direction: an `alert_ack { id }` from `AgentGateway.onAlert` after `onAgentAlert` commits, with the outbox deleting an entry only on that ack. Never drop `anti_theft` / `security_violation` entries for space.
2. **`alert`: a resend after staff acknowledged the alert creates a duplicate.** The dedup only matches *unacknowledged* alerts (`findRecentOpenAlert`, `acknowledged: false`). The dedup lock also fails open when Redis is slow (`withAlertLock`), so two concurrent copies can both insert. Fix direction: a unique key on the agent's alert id, or on (machine, type, `occurredAt`), whatever the acknowledged state.
3. **System `LOCK` for runout: lost when an online station does not ack it.**
   - `resolveUndelivered` applies server state only to *staff* LOCKs. A runout LOCK that times out ends TIMEOUT, and the session stays ACTIVE with `lockReason = runout`.
   - `SessionLoginService.lease` returns 0 only for a *PAUSED* session with a held lock. So the station keeps getting full leases, metering continues, and settlement ends with a shortfall.
   - Fix direction: treat a held `lockReason` as lease 0 whatever the status, or apply a runout LOCK from server state like a staff LOCK.
4. **`login_request` / `login_result` / session `UNLOCK`: an accepted login whose answer is lost cannot be retried.**
   - `login` spends the PIN before `login_result` is written. If the socket drops at that point, or the UNLOCK is not acked, the gamer sees a failure and retypes the PIN, which gets `pin_used`.
   - On reconnect, the station does not report the session. `reconcile` then settles it as `station_dropped`, and the booking ends unplayed.
   - No money is taken and nothing unlocks, so it fails closed. But a retry is not safe twice, and the gamer loses the booking.
   - Fix direction: accept a repeat of the same PIN on the same station for the session it just spent, and answer it with the same session and a fresh UNLOCK.
5. **`state_report`: its billing handling is not retried.** `StationLinkService.reconcile` runs inline in the gateway, and a failure is only logged (`AgentGateway.handleMessage`). After a backend restart, presence has no in-memory session for the station, so `reconcile` is the only path that settles a session the station dropped. If it fails, the session waits for the sweep at its window end, and the offline time played after a single-station drop (`billSingleDrop`) is never billed. Fix direction: queue the reconcile as a station-events job with a deterministic id, like `settle` and `status`.
6. **`station_credential`: a station offline past its token's expiry cannot reconnect.** The renewal is offered only on a connect while the token is near expiry. A station that stays offline across that window locks itself out and needs to be enrolled again. This fails closed, but it is listed because it is a security message that can be lost for good.

Every other message meets the rule. Money and lock state are carried by state the agent restates (heartbeat, state_report), by commands that are re-sent with the same id, or by server-side application (staff LOCK / END_SESSION, settlement keyed on `session-settlement:<id>`). Telemetry, `peripheral_status`, `catalog_status`, `installed_games` and `session_notice` are best effort by design.
